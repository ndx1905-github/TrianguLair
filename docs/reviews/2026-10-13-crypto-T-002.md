# T-002: independent review of the crypto prototype (packages/crypto)

- **Date:** 2026-10-13
- **Reviewer:** independent agent (did not write T-001)
- **Scope:** `packages/crypto` at commit `da261e5` (all of `src/`, `test/`, `README.md`, `THREATS.md`), checked against `docs/SPEC.md`: Architecture (Invitation link and return link, Encrypted sharing, Organization on the storage, Format versions), First launch (Recovery kit, Adding a device, Loss and theft), Data model (signed index), and Privacy/security (Threat model).
- **Method:** line-by-line reading, plus experiments run against the library. Every finding marked *(test)* has a demonstration in `packages/crypto/test/review-t002.test.ts`. Each one is an `it.fails(...)` that states the **desired** behaviour. It fails today, so the suite stays green. When the fix lands, the test starts passing, `it.fails` reports an error, and the test has to be turned into a plain `it(...)`. `src/` was not modified.
- **Build:** `npm install --workspaces=false` reported 0 vulnerabilities. `npm test` gives 8 original files with 65 tests passing, plus 12 new expected failures. `npm run typecheck` is clean.

## Summary

The prototype is careful work. The primitives are standard libsodium constructions and are used correctly. Nonces are random 192-bit values under single-use keys. The protected header is bound as AEAD associated data. Signatures are domain-separated. Versions are checked strictly, unknown fields are rejected, base64url decoding is strict, and the error taxonomy is clean. Wrap anonymity is done properly: the dummy wraps are real sealed boxes, and the shuffle is unbiased. I found **no critical cryptographic break** in the code itself.

The serious problems are at the **key-management and protocol level**. As built, the format cannot deliver two promises the spec makes:

1. **Theft recovery without changing identity.** Every full device holds the root seed and the master key, so a thief can derive every future sharing key and can certify keys of their own.
2. **"The invitation key is removed upon acceptance or expiry."** The documented flow only re-wraps, so an intercepted link keeps working for every pack that ever carried the invitation wrap.

Both have to be decided before T-201 freezes the v1 format.

## High

### F-01: Sharing-key rotation does not survive the theft of a full device, and a thief can take over the identity *(test)*

**Where:** `src/identity.ts:27` (`Identity.rootSeed`), `src/identity.ts:65`, `src/identity.ts:72-78` (sharing key = `crypto_kdf(root, rotation)`), `src/transfer.ts:119-121` (a full-device export ships `root`), `src/identity.ts:155-160` (any higher rotation is accepted). On the spec side: "Loss and theft" and "Adding a device".

**Problem.**

- A full device persists `rootSeed`, which is exactly as powerful as the 12-word phrase. The spec says the phrase is "never stored on the device after setup", but its equivalent is stored.
- Sharing keys are derived from the root at a public counter. A thief who extracts the device keys can compute `deriveSharingKeyPair(root, r+1)` and read everything friends wrap to the "new" key after "Declare a device lost". Step 2 of the theft flow ("the thief no longer sees any update") therefore does not hold.
- The thief also holds the master signing key. They can `issueSharingCert(…, { rotation: r+100 })` for a key of their own. Friends "accept it automatically" (spec, Loss and theft, step 3) because `verifySharingCert` only checks `rotation >= lastSeen.rotation`. The owner and the thief can then outbid each other forever, and friends cannot tell which of them is legitimate.

THREATS.md does say "a leaked phrase compromises past and future sharing keys". But the spec's theft flow assumes that a *device* compromise is weaker than a *phrase* compromise, and in this design it is not.

**Fix (pick one and write it into the spec):**

- **(a) Recommended.** Keep master/root material **off everyday devices**.
  - Devices hold only a *device key* (Ed25519) plus the current sharing key (random, **not** derived from the root).
  - The master signs a `device-cert` for each device key. The device key signs indexes and packs.
  - The current sharing secret is stored in the recovery vault, encrypted under a key derived from the root. Restoring from the phrase therefore still restores everything.
  - "Declare a device lost" then requires the phrase, or a device explicitly designated as holding the master. It publishes a master-signed device revocation and a new sharing cert. A thief holding only a device key cannot issue sharing certs.
- **(b) Minimum.** Make sharing keys random instead of root-derived, and stop persisting `rootSeed` on devices (persist only the master secret key). This stops the derivation of future keys. It does not stop certificate hijacking, so the spec must then state that theft of a device holding the master equals identity compromise. The mitigation becomes the non-extractable key in Keychain/Keystore and "start a new identity".
- In both cases, make `encodeKeyExport({ identity })` an explicit "primary device" path. Make `{ sharing }`, or a device cert, the default for "Adding a device".

### F-02: Intercepted invitation links stay valid past acceptance and expiry, and anyone holding the link can answer first

**Where:** `src/invitation.ts:72-96` (bearer link carrying the X25519 secret), `src/invitation.ts:179-205` (any valid response is accepted, with no single-use state), README "Invitation" step "then `rewrapPack(...)` drops the invitation wrap", `src/pack.ts:226-234`. On the spec side: "Invitation link and return link" ("it is removed upon acceptance or expiry") and the threat-model row "Access to my messaging".

**Problem.**

1. **Persistence.** The documented acceptance flow is `rewrapPack`. That leaves the batch key unchanged, so whoever kept the link (messaging history, cloud backup of the chat, a link previewer) can open every version of every pack that carried the invitation wrap for as long as the ciphertext is unchanged. Packs are rewritten only when their content changes, so that can be months. Expiry is enforced only by honest clients (`assertInvitationActive`). A modified client ignores it, and the owner removes nothing at expiry unless the app is running and sweeps. The threat model accepts "using an intercepted invitation **during its validity**", but this goes well beyond that.
2. **Who answers first.** Every link holder can produce a valid `invitation-response`. The owner's `openInvitationResponse` accepts any number of responses for the same invitation and cannot tell them apart. The safety-code comparison that THREATS.md and the spec rely on does not exist yet. By default the owner then grants "everything I share with friends" to whichever key answered.

**Fix:**

- **Acceptance** (first verified response) and **expiry**: run `reencryptPack`, not `rewrapPack`, on every pack that carried the invitation wrap. Document this in the README flow, and add a helper `retireInvitationKey(packs, ownerKeys, recipientsFor)` so the right primitive is the easy one to call.
- At expiry, the owner app must actively sweep. Invitation keys should be tracked in the recovery vault so that another device can perform the sweep.
- Make an invitation **single-use** on the owner side. Store `{invitationId → acceptedResponder}`. If more than one distinct responder answers, show a warning ("this invitation was answered by 2 people, it may have been intercepted") and do not accept any of them silently.
- Until out-of-band verification is done (see Q5), grant a reduced default scope or require an explicit confirmation showing the responder's fingerprint.
- Consider scoping the invitation key to a **dedicated invitation pack set** (a snapshot of the "friends" content made for this invitation) instead of adding its wrap to the live packs. Retiring it then means deleting those files, and no re-encryption is needed.

## Medium

### F-03: Low-order X25519 keys are accepted in sharing certificates and break `sealPack` with a raw libsodium error *(test)*

**Where:** `src/identity.ts:147` (`parseKey` only checks the length), `src/encoding.ts:156-159`, `src/pack.ts:105-107`.

**Problem.** A friend can certify an all-zero key, or another small-order point. `verifySharingCert` accepts it. Later, every `sealPack` that includes that friend fails with a generic `Error: invalid usage`, which is not a `TLCryptoError`. Publishing of every pack shared with them is blocked (a DoS against the owner), and the app's `switch (err.code)` handling is bypassed. There is no loss of confidentiality, because libsodium refuses to seal.

**Fix:** in `verifySharingCert`, and wherever an X25519 public key is parsed from untrusted input, reject keys for which `crypto_scalarmult(random, pk)` throws or returns all zeros, or check against the small-order blacklist. In `makeWraps`, wrap `crypto_box_seal` in a try/catch and throw `FormatError('pack: invalid recipient key')`.

### F-04: The monotonic `updated` check lets one wrong clock lock readers out permanently *(test)*

**Where:** `src/signed-index.ts:105-107`.

**Problem.** `checkNoRollback` rejects any index whose `updated` is earlier than the last one seen. Suppose a device publishes once with a clock far in the future (a dead RTC battery, a manual date change, or a thief with the key). Every reader who saw that index rejects all later honest indexes until real time catches up, possibly in 2099. There is no recovery path.

**Fix:** make `seq` the **only** ordering criterion. Treat `updated` as informational. At verification, reject an `updated` value that is more than about 24 hours ahead of the reader's clock (`FormatError`, retry later). Never use `updated` for rollback decisions. See Q1.

### F-05: Signed JSON is not required to be canonical on input (duplicate keys, parser differentials) *(test)*

**Where:** `src/encoding.ts:100-111`, `src/sign.ts:25-34`, `src/pack.ts:138` (the pack header is not required to be canonical either).

**Problem.** Verifiers parse the transported JSON and then re-canonicalize. `{"seq":999,"seq":1,…}` verifies as `seq: 1` because `JSON.parse` keeps the last duplicate. A Swift, Kotlin or Rust reader that keeps the first duplicate, or rejects duplicates, will see a different document, or the same signature over different semantics. This is a classic signature parser-differential, and the spec explicitly plans other implementations ("public specification … test vectors … cross-reading tests"). Pack headers are malleable in the same way: whitespace or key order can change while the pack still opens and its etag changes. That is harmless today thanks to the etag check, but it makes test vectors ambiguous.

**Fix:** for every string or byte input of a signed document or pack header, require `canonicalize(JSON.parse(s)) === s` and throw `FormatError('non-canonical')` otherwise. This rejects duplicates, whitespace and key-order variants in one rule. Keep accepting already-parsed objects only for in-process use. Specify "transported bytes MUST be canonical" in the v1 spec.

### F-06: Packs, including group-key packs, have no sender authentication, and no API enforces the index check *(test)*

**Where:** `src/group.ts:50-62`, `src/pack.ts:215-219`. THREATS.md, "No sender authentication inside a pack".

**Problem.** Sharing public keys are public, so anyone can produce a pack, or a group-key pack, that `openPack` or `openGroupKey` accepts. Authenticity relies entirely on callers first checking `packEtag(bytes)` against a verified index. Nothing in the API forces that check, and the obvious call (`openPack`) skips it. A former member who knows the group id can forge `{group: id, generation: n+1, secretKey: <theirs>}`. If the app keys group secrets by `(id, generation)` and keeps the highest generation, the member stops being able to read the owner's group-wrapped content, and any content the app later wraps "to the group" goes to the attacker. Trial decryption of unauthenticated input is also the 4096-wrap DoS vector.

**Fix:**

- Add `openIndexedPack(bytes, verifiedIndex, file, keys)`, which checks the etag **before** any X25519 operation, and make it the documented entry point. Mark `openPack` as low-level.
- Bind group-key packs to their owner: add `owner` to the group-key payload, and accept a group-key pack only if it is listed in that owner's verified index. Otherwise, sign the payload with the owner's (device) key.
- State in the spec that "Everything is signed with my key" is achieved *through the index*, and that any pack not reached through a verified index entry MUST be ignored.

### F-07: Sharing-certificate freshness is outside rollback protection

**Where:** `src/identity.ts:137-161`. The spec does not define how certs are published.

**Problem.** `verifySharingCert` without `lastSeen` accepts any old certificate. A friend with no state for the owner (a new friend, a reinstall, a restored device) can be served a **stale certificate for a stolen key** by the storage or by an attacker. That friend then wraps content to a compromised key. Certificates have no expiry and no revocation, and they are not covered by the index's `seq`.

**Fix:** embed the owner's current sharing cert, the device certs and the device revocations **inside the signed index** (or reference them by hash). They then inherit `seq` rollback protection, and a reader needs exactly one freshness anchor per owner. Persist the last accepted cert per contact in the recovery vault, so that a restore does not reset to TOFU.

### F-08: Pack sizes are not padded, although the spec promises padding

**Where:** `src/pack.ts:165-174` (the ciphertext is exactly `payload + 16`). Spec: "the app adds padding to limit what can be inferred". THREATS.md, "Metadata leaks".

**Problem.** The size of a pack reveals the size of its payload, for example the number of places in a batch or whether a comment was added. Padding has to sit *inside* the AEAD plaintext with an unambiguous framing, so it is a **format** decision and cannot be left to the app.

**Fix:** in v1, define the plaintext as `u32 length ‖ payload ‖ zero padding`, padded to a bucket (Padmé, or a power of two up to 64 KiB and then 64 KiB multiples). Check the padding on open: it must be zeros, and the declared length must not exceed the plaintext. Add a `pad: 'none' | 'padme'` field to the protected header so that the choice is visible and covered by the AD.

## Low

### F-09: Transfer code: entropy is adequate, but the format lacks expiry and binding, and the parameters are not floored on encrypt

**Where:** `src/transfer.ts:45-50`, `66-79`, `81-102`.

**Analysis.** 12 Crockford characters give 60 bits. With Argon2id at 2 passes and 64 MiB, a well-funded attacker computing on the order of 10⁴ to 10⁵ guesses per second per GPU needs about 2⁵⁹ / 10⁵ seconds, roughly 180,000 GPU-years on average. That is fine for a blob that lives 15 minutes, and acceptable even if the blob is kept, because the storage read address is public. Remaining issues:

- The spec says "a 6-word code". 6 BIP39 words give 66 bits, but 6 words from a short list such as EFF's 1,296 words give only 62 bits. Pick one and align spec and code. **Do not go below 60 bits.**
- `encryptForTransfer` accepts `opslimit=1, memlimit=8 KiB`. Floor it at `OPSLIMIT_INTERACTIVE` and `MEMLIMIT_INTERACTIVE`.
- `decryptTransfer` accepts up to 1 GiB from attacker-controlled bytes. Cap it at 256 MiB on mobile.
- "Expires after 15 minutes, works only once" exists only in the spec. Add an `expires` field to the header (covered by the AD) and have the receiver reject expired blobs. Single use still depends on deletion from the storage.
- The payload is not bound to a purpose. Put `type: "key-export"` inside the AD-covered header, or derive the key with a context string, so that a future second blob type cannot be confused with this one.

### F-10: DoS bounds: 4096 wraps, and the `padTo` loop runs before its bound check

**Where:** `src/pack.ts:49`, `src/pack.ts:108-113`.

**Problem.** `MAX_WRAPS = 4096` times a few candidate keys means tens of thousands of X25519 operations in WASM. Separately, `sealPack(…, { padTo: 5000 })` spends about 4.5 s generating key pairs and only then throws.

**Fix:** check `target > MAX_WRAPS` before the loop. Lower `MAX_WRAPS` to 256, since the spec expects tens of recipients and power-of-two padding needs at most 256. Verify the etag before any trial decryption (see F-06).

### F-11: The signed index accepts arbitrary `file` and `public` strings *(test)*

**Where:** `src/signed-index.ts:78-86`.

**Problem.** A followed person, who is untrusted from my point of view, can list `https://tracker.example/x.gif` or `../../other-user/…`, which could turn my app into a URL fetcher (an IP-tracking beacon, or SSRF on a LAN WebDAV server). Duplicate `file` entries are also accepted.

**Fix:** require relative paths matching `^(packs|media|public)/[A-Za-z0-9_-]{1,64}\.(bin|geojson)$`, no duplicates, and an `etag` that is valid base64url of the expected length.

### F-12: Invitation response binding and validation gaps

**Where:** `src/invitation.ts:162-173`, `198`, `118`.

**Problems and fixes:**

- The signed response covers only `invitation: <id>`, not the inviter's owner key or the invitation key. A link holder who reads a response (it is sealed to a key they hold) can replay it into a self-made invitation that reuses the same id, and so present "Bob asked to follow me". The impact is low, because Bob's keys are public anyway. **Fix:** sign `inviter` (owner id) and `invitationKey` as well.
- The response's `created` is not checked against the invitation's `[created, expires]` window. **Fix:** check it.
- `location` is any string. **Fix:** require an `https://` URL with no credentials and no fragment.
- The spec's step 2 says the return link carries "the address of their own content if they also share". The response has no `location` field. **Fix:** add an optional one.
- The return response is 647 bytes, or 863 base64url characters. That is too large for a comfortable QR code (see Q4).

### F-14: Secret hygiene (best effort, but cheap to improve)

**Where:**

- `src/identity.ts:53-56`: `entropy` and the caller's `rootSeed` are not wiped.
- `src/identity.ts:62`: `masterSeed` is not wiped.
- `src/identity.ts:75`: the sharing `seed` is not wiped.
- `src/pack.ts:202-207`: `batchKey` is not wiped when the AEAD fails and the loop continues.
- `src/pack.ts:226-234`: `rewrapPack` decrypts the whole payload only to obtain the batch key, and never wipes the payload.
- `src/group.ts:52-60`: the plaintext containing the group secret is not wiped.
- `src/transfer.ts:119-125`: the root is put into an immutable JS string.

**Fix:**

- `memzero` all intermediates in `finally` blocks.
- Split `openInternal` so that it returns the batch key after unwrapping and checking the tag, without keeping the plaintext. Use the detached AEAD API, or decrypt and then wipe.
- Build key-export and invitation payloads as bytes, without passing through `canonicalize` strings, where possible. Document that secrets inside strings cannot be wiped.
- Remove `rootSeed` from `Identity` once F-01 is fixed.

### F-15: Error messages and oracles

**Where:** `src/encoding.ts:83`, `src/pack.ts:210-211`.

**Problem.** `canonical JSON: … (got ${value})` echoes the rejected number. If someone ever puts a coordinate into a signed structure by mistake, it ends up in logs and crash reports. The `DECRYPT` vs `NO_MATCHING_KEY` distinction tells you whether a wrap was addressed to one of your keys. That is fine locally, but it must never be reflected to a remote party.

**Fix:** drop the value from the message. Document that error codes are local-only.

## Notes

### N-1: Primitive choice and usage are sound

- **Ed25519** (libsodium verification rejects non-canonical signatures and small-order keys) is used for signatures only.
- **X25519 sealed boxes** are used for wraps.
- **XChaCha20-Poly1305-IETF** is used for content, with a 24-byte random nonce under a fresh 32-byte key per encryption. There is no nonce-reuse risk, even with `rewrapPack`, because the ciphertext is untouched.
- **Argon2id13** derives the transfer key, with a fresh 16-byte salt. Its AD covers the full 53-byte header, so parameter, salt and nonce tampering are all detected.
- **BLAKE2b keyed by the BIP39 entropy, then `crypto_kdf`** derives the identity keys, with distinct 8-byte contexts (`TLmaster` with id 1, `TLshare_` with id = rotation). Master and sharing keys are properly separated, and no Ed25519→X25519 conversion is used.
- Deviating from BIP39's PBKDF2 seed is fine and even desirable, since the phrase cannot be confused with a wallet seed. 128 bits is adequate.

### N-2: Domain separation and canonical JSON

- The prefix `"TrianguLair-signature-v1\n" + domain + "\n"` plus a `type` field in every document gives two independent layers of separation.
- Canonicalization matches JCS for this value domain: UTF-16 code-unit sort, `JSON.stringify` escaping including lone surrogates, and integers only. Forbidding floats is a good choice.
- The signature covers every field except `signature`. That was verified for the cert, the index, the invitation and the response.
- The only gap is input canonicality (F-05).

### N-3: Wrap anonymity holds

- Dummy wraps are genuine sealed boxes to throwaway keys, so their ephemeral keys are valid curve points just like the real ones.
- The Fisher–Yates shuffle uses `randombytes_uniform`, which is unbiased.
- No recipient bytes appear in the header (tested).
- Remaining leaks are the power-of-two wrap count and the payload size (F-08).
- Keep the "no hint" decision. If one is ever needed, derive it per pack from the batch key, so that only recipients can compute it.

### N-4: AEAD associated data is correct

The AD (`TLPK ‖ version ‖ canonical protected header`) binds `id`, `nonce`, `alg`, `wrapAlg`, `type` and `version`. Leaving `wraps` outside the AD is a sound JWE-style choice, because the etag covers the whole file. For v1, consider adding the owner id to the encrypted payload. A recipient copying the pack into their own index could then not re-attribute it, although they can already copy the plaintext.

### N-5: Rollback and fork detection

- `seq` together with "same seq, different content = fork" is the right primitive.
- Limits:
  - Split-view (different readers being served different indexes) is undetectable without gossip.
  - Two of the owner's devices racing on a storage without conditional writes (HTTPS-only mode) produce a legitimate same-`seq` fork, which readers will report as an attack.
- Recommendations:
  - Allocate `seq` with `If-Match` on the index file.
  - Have readers treat a fork as "warn and wait for the next higher seq" rather than as a hard failure.
  - Optionally add `prev` (the hash of the previous index) in v2.

### N-6: Test gaps

Tests worth adding before T-201 (several of them are now covered by `review-t002.test.ts`):

- **Known-answer vectors:** phrase → owner id, rotation-n sharing public key, exact signed bytes for each domain, a fixed pack decoded with a fixed key, and a transfer blob with fixed salt and nonce. These are required for the "public specification with test vectors" item in the spec.
- **Fuzz and property tests** on `decode`, `parseInvitationLink`, `verifyIndex`, `decryptTransfer` and `decodeKeyExport`: only `TLCryptoError` may ever escape. F-03 and F-13 show that this is not true today.
- An end-to-end revocation test that also checks invitation-key retirement (F-02) and group rotation followed by a forged group-key pack (F-06).
- Index-plus-etag integration: a pack whose etag mismatches must be rejected before trial decryption.
- Multiple responses to one invitation.
- An old certificate presented without `lastSeen`.
- Duplicate-key and non-canonical JSON inputs for every signed type.
- A statistical check that real and dummy wraps are indistinguishable (byte-distribution sanity check only).

## Decisions on the 5 open questions from T-001

### Q1: Add `seq` to the signed index? **Yes, make it required and the sole ordering key.**

- `seq` is a u53 that increases by exactly 1 per publication. It is allocated with a conditional write (`If-Match` on the index). In HTTPS-only mode it is allocated by the single publishing device.
- Rollback rule: reject `seq < lastSeen.seq`, and treat `seq == lastSeen.seq` with different bytes as a fork (warn, keep the old one, accept the next higher `seq`).
- `updated` becomes informational: reject only values more than 24 hours in the future, and never use it for ordering (F-04).
- Also put into the index the current sharing cert, the device certs and revocations, and the list of readable format versions that the spec requires. All of them then inherit the same freshness anchor (F-07).
- Persist `lastSeen` per owner in the recovery vault, so that a restore keeps its anchors.
- Update the spec's index example, which currently has no `seq`.

### Q2: Index `etag`: content hash or storage ETag? **Content hash.**

- The storage ETag is backend-specific. It may be opaque (WebDAV), unrelated to the content (multipart S3), changed by re-upload or copy, and unknown until after the upload, so it cannot be signed in advance. It also authenticates nothing.
- A content hash is verifiable by any reader on any backend and is what makes the signature cover the pack.
- Rename the field to `hash`, with an algorithm prefix and **256 bits**: `"hash":"b2b256:<b64url 32B>"`. 128 bits is fine for second preimages, but auditors will ask, and the cost is 22 extra characters per entry.
- Keep the storage ETag only as a local cache validator (`people.last_etag` and a per-file `If-None-Match`), never inside signed data.
- This pairs naturally with content-addressed file names (see Q3).

### Q3: Stable pack id across re-encryption? **A stable logical id, but not in the clear.**

- A stable id is useful to readers (What's new diffs, cache replacement, CRDT linkage).
- Today it is a cleartext, AD-bound header field that never changes. The storage and a revoked friend can therefore link every future version of "the pack I used to read" and observe its update times and sizes after revocation.
- Recommendation:
  - Move the logical id **inside the encrypted payload**.
  - In the cleartext header, drop `id`. The random `nonce` already identifies the encryption uniquely and is in the AD.
  - Store packs under **content-addressed names** (`packs/<b64url(hash)[0..22]>.bin`).
- Re-encryption then yields an unlinkable new file. The signed index maps the current set of files, readers diff by logical id after decryption, and immutable files remove overwrite races between devices.
- The cost is an extra delete of the old file per update, which the spec's "occasionally merges … and deletes files" already plans for.

### Q4: Invitation link size (about 600 characters) and QR codes? **Switch to a compact binary encoding of about 300 characters. Use a direct key exchange for in-person QR.**

- Measured: 622 characters without `location`, and 730 for a full URL with a typical Nextcloud share address.
- That needs roughly a version 22 QR code at error-correction level M (105×105 modules). It scans from a phone screen, but it is fragile when printed small or on low-end cameras. Messaging apps may also truncate or preview it.
- Most of the size comes from double encoding (base64url of JSON containing base64url) and redundant fields.
- v1 binary invitation layout:
  - magic and version: 2 B
  - `id`: 16 B
  - owner key: 32 B
  - `created` and `expires` as u32 seconds: 8 B
  - invitation secret: 32 B. The public `key` field is dropped, because it is derived from the secret.
  - `location` as a length-prefixed UTF-8 string
  - Ed25519 signature: 64 B
- That totals about 200 B with a typical location, or about 270 base64url characters. Prefixed with `https://example.org/i#`, it is about 300 characters, roughly a version 13 QR code at level M (69×69). Base32 in QR alphanumeric mode can shave a bit more.
- Keep the signature: it binds `location` and `expires` to the owner key at a cost of 64 B.
- For **face-to-face** exchange, do not use the invitation at all. Exchange `owner key ‖ sharing cert ‖ location` directly in both directions by QR. Proximity authenticates it, and no bearer secret is created.
- Apply the same compaction to the return response (currently 863 characters).

### Q5: Out-of-band verification of the return link (safety number)? **Yes, mandatory in the UI before the first grant, using a full-strength pair fingerprint.**

- Define `safetyNumber(A, B) = BLAKE2b-256("TrianguLair-safety-v1" ‖ min(pkA, pkB) ‖ max(pkA, pkB))` over the two **master** public keys. Render it as 12 groups of 5 digits (about 200 bits shown, Signal-style), or compare it by scanning a QR code.
- **Do not use a short 6-digit or 4-word code without a commitment scheme.** An interceptor who holds the link can grind their own key pair offline until the short code collides with the legitimate one. A 20-bit code costs about 10⁶ key generations, which takes seconds.
- UI:
  - Show the requester's name, fingerprint and the "N responses to this invitation" counter (F-02).
  - Default to "unverified". Grant the default "friends" scope only after "I compared the code", or after an explicit "accept without verifying" with a warning.
  - Persist the verified state and alert if the contact's master key ever changes.
- A QR exchange face to face counts as verification.
- Add `safetyNumber()` to `@triangulair/crypto`, with known-answer vectors.
